# AGENTS.md — src/apps/admin/inventory/

## What belongs here

The inventory ledger and admin stock adjustments: listing stock movements, incrementing (restock) or decrementing (removal) product stock, rewriting an already-recorded restock, and reverting an already-recorded restock or removal. Also the listener that records the stock movements driven by the order lifecycle.

## What does NOT belong here

- Product catalog management (CRUD, ordering, soft-delete) → the products sub-module.
- The order-flow stock decrement on order creation → owned by the order modules; this sub-module only **records** the resulting movement via its listener.
- Profit / cost reporting → the admin dashboard's `summary` reading reads the `ADMIN_RESTOCK` movement lines via Prisma (not through this service) and reduces `price × quantity` in memory for its `restockCost` and `profit` figures. The stored unit cost (`Math.round(totalCost / quantity)`) on a restock line is contract for that calculation — see `src/apps/admin/dashboard/AGENTS.md`.

## Core Patterns

- **Ledger model**: every stock change is recorded as a movement record (with its line items) tagged with an **origin**. A record's `origin` and `createdAt` never change, and only the two admin-driven origins are writable after the fact, with different powers: a restock, while it is still editable, can have its lines rewritten **or** be reverted away entirely; a removal can only be reverted, and has no editability window at all (see below). Every order-driven record is append-only. Quantities are stored as **positive integers** — the origin, not the sign, encodes the direction (order creation and admin removal reduce stock; order/admin cancellation and admin restock increase it).
- **Order-driven movements**: an event listener reacts to order created/cancelled events and writes the movement. The cancelled event carries the origin so the listener does not infer it.
- **Admin-driven movements**: restock and removal mutate stock and write the movement **inside the same transaction**. Restock takes a **`totalCost` per line** (not a unit price) and stores the derived, rounded unit cost (`Math.round(totalCost / quantity)`) — the column is an integer, so the division is always rounded before persisting; removal snapshots the product's current sale price.
- **Atomic stock mutation**: both directions use a guarded conditional update filtered on non-deleted products. Decrement additionally guards on `stockQuantity >= quantity`; on a zero-row result, a follow-up lookup distinguishes "product not found" from "insufficient stock", each mapped to an `adminInventory` error. Increment uses the same guard, where a zero-row result can only mean "not found". Soft-deleted products are treated as not-found by both.
- **Duplicate guard**: a batch is rejected up front when the same product appears twice, so a single movement can never carry two lines for the same product. A unique constraint on the line table is the backstop, and its violation is **not** translated — the service check is what keeps it unreachable.
- **Listing**: movements are returned paginated (newest first) with their order and product relations, following the standard page-object contract. The listing accepts no sort input, but the fixed order still ends on the id: `createdAt` is not unique, so movements committed in the same millisecond would be sliced differently on each page request. Filterable by `origin` and by a set of product ids.
- **Editable flag**: every item carries an `editable` boolean, meaning "this movement still accepts some write" — not necessarily a line rewrite. It is always `true` for an `ADMIN_REMOVAL` item (which has no window, but whose only write is the revert), and `true` for an `ADMIN_RESTOCK` item only when no `ORDER_CREATION` or `ADMIN_REMOVAL` movement has happened since it, across the **entire ledger** — not just the current page or filtered set. Other origins occurring after a restock (another restock, an order/admin cancellation) do not affect its editability. Every order-driven origin always carries `editable: false`. The check runs as an extra unfiltered `findFirst` for the latest disqualifying movement inside the same transaction as the listing query. Note the disqualifying set can also **shrink**: an `ADMIN_REMOVAL` is itself disqualifying and reverting one deletes it, so a removal revert can re-open the window on an older restock that was blocked by it. That stays sound — the removal's stock effect is undone in the same transaction, and `ORDER_CREATION` rows are never deleted (a cancellation appends a new record instead of removing one) — but it means the predicate is not monotonic over time. `id` is a random UUID (not a sortable/monotonic column), so the comparison uses `createdAt` alone; a restock sharing the exact same millisecond as a disqualifying movement is conservatively reported as not editable.
- **Editing and reverting**: while an `ADMIN_RESTOCK` movement still satisfies the editable predicate above, it accepts two writes — a rewrite of its lines, and a full revert. An `ADMIN_REMOVAL` accepts the revert alone, and accepts it forever: the predicate is skipped for it, since putting stock back can never fail on balance. A revert undoes the movement's whole effect on stock and deletes the movement (its lines cascade with it), leaving no compensating record behind; the **direction of the revert delta comes from the origin** — a restock's quantity goes back out of stock, a removal's comes back in. All three writes run the same load-lock-and-guard step, which takes the set of origins it accepts as an argument and only applies the timestamp window to a restock. The write paths and the listing flag share the **comparison helper**, so the timestamp rule itself has one home — but the surrounding checks do not: the origin gate and the lookup of the latest disqualifying movement each exist twice, once for the flag and once for the writes, and both sides also encode the restock/removal asymmetry, so widening the disqualifying-origin set — or changing which origins are writable — means touching both. The payload is a **full replacement** of the movement's lines, and create and update share one exported line DTO class so the two bodies cannot drift; a line can be added, dropped, or have its quantity/cost changed. The movement's `origin` and `createdAt` are never touched — `createdAt` places it in the ledger, decides its own editability, and buckets it in the dashboard's restock cost.
- **Movement write concurrency and stock delta**: all three writes open their transaction by taking a **row lock on the movement** (raw `SELECT … FOR UPDATE`) before reading the lines. The lock is what makes them safe: the stock change is derived from the lines read under it, so two concurrent writes would otherwise each apply the same effect — stock counted twice on a double revert, a doubled delta on a double edit. Product rows are locked in a **fixed order** (by product id) on every write — the loaded lines are ordered and the edit sorts its delta map before applying — so two concurrent writes touching the same products cannot deadlock by taking those locks in opposite orders. Stock is then reconciled per product by a **signed delta** (old quantity out, new quantity in) — a zero delta writes nothing, and the stock-floor guard is attached only when the delta is negative, so it is a variant of the guarded update, not the increment/decrement path itself. A revert is the same machinery with the delta fixed at the full opposite of each line — negative for a restock, **positive** for a removal. A removal revert therefore never attaches the floor guard and can only fail as not-found (product soft-deleted since the removal), while the edit and the restock revert also inherit the insufficient-stock mapping, on top of the shared not-found / not-editable errors; the batch duplicate guard applies to the edit only, since a revert carries no payload.
- **The eligibility rule trails the stock it guards**: an order decrements stock inside its own transaction and only emits the event afterwards, so the `ORDER_CREATION` row lands in a **later** transaction. For that window a restock still looks eligible although the stock it added is already spoken for, and a write in that window under-counts stock (or trips the floor guard and reports insufficient stock). The movement-row lock cannot close this — the racing writer never touches that row. Closing it properly means writing the order-driven movement inside the order transaction; until then, treat the predicate as eventually, not immediately, consistent.

## Conventions

| Rule | Detail |
|---|---|
| Positive quantities | Movement quantity is always positive; direction comes from the origin |
| Atomic admin adjustments | Stock update and ledger write share one transaction |
| Guarded decrement | Distinguish not-found from insufficient stock via a follow-up lookup |
| Reject duplicates early | Validate product uniqueness in a batch before writing |
| Lock before a read-modify-write | Any movement write — a restock edit, a restock revert, a removal revert — locks the movement row before reading the lines it derives the stock change from |
| Lock product rows in a fixed order | Every movement write touches product rows ordered by product id, so concurrent writes cannot deadlock |
| Errors | Throw `AppException` with `adminInventory` codes; values live in the API contract reference |
