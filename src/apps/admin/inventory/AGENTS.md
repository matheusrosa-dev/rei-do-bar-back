# AGENTS.md — src/apps/admin/inventory/

## What belongs here

The inventory ledger and admin stock adjustments: listing stock movements, incrementing (restock) or decrementing (removal) product stock, and rewriting or reverting an already-recorded restock. Also the listener that records the stock movements driven by the order lifecycle.

## What does NOT belong here

- Product catalog management (CRUD, ordering, soft-delete) → the products sub-module.
- The order-flow stock decrement on order creation → owned by the order modules; this sub-module only **records** the resulting movement via its listener.
- Profit / cost reporting → the admin dashboard's `summary` reading reads the `ADMIN_RESTOCK` movement lines via Prisma (not through this service) and reduces `price × quantity` in memory for its `restockCost` and `profit` figures. The stored unit cost (`Math.round(totalCost / quantity)`) on a restock line is contract for that calculation — see `src/apps/admin/dashboard/AGENTS.md`.

## Core Patterns

- **Ledger model**: every stock change is recorded as a movement record (with its line items) tagged with an **origin**. A record's `origin` and `createdAt` never change, and only one origin is ever writable after the fact: a restock, while it is still editable, can have its lines rewritten or be reverted away entirely (see below). Every other record is append-only. Quantities are stored as **positive integers** — the origin, not the sign, encodes the direction (order creation and admin removal reduce stock; order/admin cancellation and admin restock increase it).
- **Order-driven movements**: an event listener reacts to order created/cancelled events and writes the movement. The cancelled event carries the origin so the listener does not infer it.
- **Admin-driven movements**: restock and removal mutate stock and write the movement **inside the same transaction**. Restock takes a **`totalCost` per line** (not a unit price) and stores the derived, rounded unit cost (`Math.round(totalCost / quantity)`) — the column is an integer, so the division is always rounded before persisting; removal snapshots the product's current sale price.
- **Atomic stock mutation**: both directions use a guarded conditional update filtered on non-deleted products. Decrement additionally guards on `stockQuantity >= quantity`; on a zero-row result, a follow-up lookup distinguishes "product not found" from "insufficient stock", each mapped to an `adminInventory` error. Increment uses the same guard, where a zero-row result can only mean "not found". Soft-deleted products are treated as not-found by both.
- **Duplicate guard**: a batch is rejected up front when the same product appears twice, so a single movement can never carry two lines for the same product. A unique constraint on the line table is the backstop, and its violation is **not** translated — the service check is what keeps it unreachable.
- **Listing**: movements are returned paginated (newest first) with their order and product relations, following the standard page-object contract. The listing accepts no sort input, but the fixed order still ends on the id: `createdAt` is not unique, so movements committed in the same millisecond would be sliced differently on each page request. Filterable by `origin` and by a set of product ids.
- **Editable restock flag**: every item carries an `editable` boolean. It is only ever `true` for an `ADMIN_RESTOCK` item, and only when no `ORDER_CREATION` or `ADMIN_REMOVAL` movement has happened since it, across the **entire ledger** — not just the current page or filtered set. Other origins occurring after it (another restock, an order/admin cancellation) do not affect editability. Every other origin always carries `editable: false`. The check runs as an extra unfiltered `findFirst` for the latest disqualifying movement inside the same transaction as the listing query. `id` is a random UUID (not a sortable/monotonic column), so the comparison uses `createdAt` alone; a restock sharing the exact same millisecond as a disqualifying movement is conservatively reported as not editable.
- **Restock editing and reverting**: while an `ADMIN_RESTOCK` movement still satisfies the editable predicate above, it accepts two writes — a rewrite of its lines, and a full revert that takes the whole restocked quantity back out of stock and deletes the movement (its lines cascade with it), leaving no compensating record behind. Both run the same load-lock-and-guard step, so the predicate is enforced identically on each. The write paths and the listing flag share the **comparison helper**, so the timestamp rule itself has one home — but the surrounding checks do not: the origin gate and the lookup of the latest disqualifying movement each exist twice, once for the flag and once for the writes, so widening the disqualifying-origin set means touching both. The payload is a **full replacement** of the movement's lines, and create and update share one exported line DTO class so the two bodies cannot drift; a line can be added, dropped, or have its quantity/cost changed. The movement's `origin` and `createdAt` are never touched — `createdAt` places it in the ledger, decides its own editability, and buckets it in the dashboard's restock cost.
- **Restock write concurrency and stock delta**: both writes open their transaction by taking a **row lock on the movement** (raw `SELECT … FOR UPDATE`) before reading the lines. The lock is what makes them safe: the stock change is derived from the lines read under it, so two concurrent writes would otherwise each apply the same effect — twice-subtracted stock on a double revert, a doubled delta on a double edit. Product rows are locked in a **fixed order** (by product id) on both writes — the loaded lines are ordered and the edit sorts its delta map before applying — so two concurrent writes touching the same products cannot deadlock by taking those locks in opposite orders. Stock is then reconciled per product by a **signed delta** (old quantity out, new quantity in) — a zero delta writes nothing, and the stock-floor guard is attached only when the delta is negative, so it is a variant of the guarded update, not the increment/decrement path itself. A revert is the same machinery with the delta fixed at the full negative of each line. Both therefore inherit the module's not-found (product soft-deleted since the original restock) vs. insufficient-stock mapping on top of the shared not-found / not-editable errors; the batch duplicate guard applies to the edit only, since a revert carries no payload.
- **The eligibility rule trails the stock it guards**: an order decrements stock inside its own transaction and only emits the event afterwards, so the `ORDER_CREATION` row lands in a **later** transaction. For that window a restock still looks eligible although the stock it added is already spoken for, and a write in that window under-counts stock (or trips the floor guard and reports insufficient stock). The movement-row lock cannot close this — the racing writer never touches that row. Closing it properly means writing the order-driven movement inside the order transaction; until then, treat the predicate as eventually, not immediately, consistent.

## Conventions

| Rule | Detail |
|---|---|
| Positive quantities | Movement quantity is always positive; direction comes from the origin |
| Atomic admin adjustments | Stock update and ledger write share one transaction |
| Guarded decrement | Distinguish not-found from insufficient stock via a follow-up lookup |
| Reject duplicates early | Validate product uniqueness in a batch before writing |
| Lock before a read-modify-write | A restock edit or revert locks the movement row before reading the lines it derives the stock change from |
| Lock product rows in a fixed order | Both restock writes touch product rows ordered by product id, so concurrent writes cannot deadlock |
| Errors | Throw `AppException` with `adminInventory` codes; values live in the API contract reference |
