# AGENTS.md — src/apps/admin/

## What belongs here

The admin backoffice, protected by HTTP Basic Auth. Each managed resource (products, categories, customers, orders, inventory, coupons, settings, notifications, delivery persons) is its own NestJS sub-module that mirrors the standard module/controller/service/`dtos` layout (some also carry an event listener, a `helpers.ts`, or custom `validators/`). Operations include catalog management, inventory movements and stock control, coupon management, activation/deactivation, guarded deletion, order listing with status management, delivery-person assignment, credential assignment for the delivery app, runtime settings management, and push notifications with a history of the manual broadcasts.

Each resource sub-module has its own `AGENTS.md` documenting its resource-specific behavior; this file covers only the conventions shared across all of them.

## What does NOT belong here

- Client-facing product or category listing → the respective modules in the store app (`src/apps/store/`).
- Customer self-management → `src/apps/store/me/`.
- Customer order placement and cancellation → `src/apps/store/orders/`.
- Anything the delivery app consumes → `src/apps/delivery-persons/`. Managing delivery persons (CRUD, credentials, revocation) belongs here; serving the entregador at runtime does not.

---

## Authentication

All admin controllers apply the admin-auth composite decorator **at class level**. It applies the **admin** Basic Auth guard and nothing else — that guard validates credentials against the admin config namespace (other audiences have their own guard and credentials — see `src/shared/guards/AGENTS.md`). Admin routes therefore require neither an `x-device-id` header nor a JWT: no guard on this surface asks for either. Nothing is bypassed — the customer guards are simply never applied here.

## Core Patterns

- **Paginated listing**: most list endpoints accept page/limit plus optional filters, a free-text search term, and optional sort key/direction; they return a normalized page object (items + pagination metadata). See `references/api-contract.md` (`.claude/references/api-contract.md` for Claude Code, `.opencode/references/api-contract.md` for opencode) for the exact pagination contract. Neither half is universal: some listings return a flat, unpaginated array (**categories**, **settings**), and some paginated ones accept no sort key or direction at all and stay fixed at newest-first (**delivery persons**, **inventory movements**, **notification history**). Each is documented in its own `AGENTS.md`.
- **Sorting strategy**: values that Prisma can order on are sorted and paginated at the database level — this **includes plain relation counts**, which Prisma expresses via `orderBy: { relation: { _count } }` (used for a customer's total orders and a coupon's usage count). Only what Prisma genuinely cannot express — a *filtered* relation count (e.g. delivered orders only) or a computed aggregate (an order's total or item quantity) — falls back to sorting in application memory via a two-step fetch (ids + the computed value, then full data for the page slice). Reach for the in-memory path only after confirming `orderBy` cannot do it — and note that a resource may also answer the cost by exposing no sort at all, as the delivery-persons listing does. **Every ordering in this app ends on a unique tiebreaker** — the id everywhere except orders, which uses `orderNumber` because it is unique *and* monotonic. Without one, ties under `skip`/`take` are sliced in whatever order Postgres returns, an order that shifts as rows are updated, so a row surfaces on two pages or on none. The rule reaches the ids query of an in-memory sort, where it looks redundant next to the sort that follows and is not (that sort is stable and merely preserves the order that arrived), and the flat listings too — nothing can be lost there without a slice, but an order that reshuffles between requests is still a defect on screen. Two exceptions need no tiebreaker and carry none: the settings listing already sorts on a unique key, and the `findFirst` probes that read the highest `sortOrder` select that column alone, so any tied row answers identically.
- **Creation defaults**: newly created catalog entities start inactive (and products start with zero stock) so they are not exposed to clients until explicitly activated.
- **Activate/deactivate**: the default is a shared private helper per resource that toggles the flag and translates the Prisma "record not found" error into an `AppException`. Several resources add rules on top: activating a product is refused while its category is inactive, deactivating a category **cascades** to deactivate its products, deactivating a coupon detaches it from every cart holding it, and **both** delivery-person toggles wipe that person's password hash (deactivation also deletes the session). A toggle that does extra work leaves the shared helper — coupons and delivery persons both split their two toggles across different paths for that reason. Toggles return the **full updated row** — there is no `select` narrowing and no serialization interceptor on admin routes, so a customer toggle does return that customer's personal fields. That openness is deliberate for operator data, but it is also why any **credential** column must be projected away at the query itself (see the conventions table).
- **Deletion**: catalog products are **soft-deleted** (deletion timestamp set) and their cart references removed atomically in one transaction. Every other resource is **hard-deleted**; the default is to hard-delete inside a transaction that first locks the row (`SELECT ... FOR UPDATE`) and then proves no dependent records exist (linked products / existing orders), otherwise a conflict error is thrown — the lock closes the race a plain pre-check-then-delete would leave open, and where the schema also has a restricting FK, the lock is the first line of defense and the FK (its P2003 translated to the same conflict) is the second. Customers and delivery persons follow this pattern; categories still use the older unguarded pre-check-then-delete — do not copy that one for a new resource. Coupons are the exception: hard-deleted with **no** pre-check, because their dependents fall to the schema's cascade / `SetNull`. Note that admin customer deletion is a plain hard delete — the *anonymization* path (scrubbing personal data while preserving orders) belongs to customer **self**-deletion in the `store/me/` module, not here.
- **Atomic stock mutations**: stock changes use a guarded conditional update (`WHERE stockQuantity >= amount`); when zero rows are affected, a follow-up lookup distinguishes "not found" from "insufficient stock". Stock-mutating endpoints live in the inventory sub-module, not in products.
- **Inventory ledger**: every stock-changing operation appends an immutable movement record tagged with an origin (order creation/cancellation, admin order cancellation, admin restock/removal). Movement quantities are stored as positive integers — the origin, not the sign, encodes the direction. Order-driven movements are written by an event listener reacting to order events; admin-driven movements are written inside the same transaction that mutates the stock.
- **Order status management**: orders expose a listing plus a status-transition endpoint. Transitions are constrained by an explicit state machine (a per-status map of allowed next statuses); an already-finalized order or an illegal transition raises the corresponding `adminOrders` error. Stock-affecting transitions run inside a transaction. An order's `total` is computed as `productsTotal - productsDiscount - couponDiscount + deliveryFee` — the coupon-discount snapshot must not be dropped.
- **Settings management**: the settings sub-module reads every runtime setting and allows updating a setting's value and toggling its active flag, keyed by the `SettingKey` enum. Most values are plain strings, but the coupon-typed setting carries a **JSON payload that is parsed and validated on write**. The client-facing read of active settings lives in the store app's `settings/` module, not here.
- **Prisma error translation**: branch on the shared predicates in `@shared/helpers/prisma-errors` (`isRecordNotFound` for P2025, `isUniqueConstraintViolation` for P2002, `isForeignKeyConstraintViolation` for P2003) — never match a raw Prisma error code inline. Coverage is **not** universal, so do not assume it: the settings sub-module has no translation at all (a missing row surfaces as a generic 500), and category rename does not handle the unique-constraint case. When you touch one of those paths, add the translation rather than mirroring the gap.

## Conventions

| Rule | Detail |
|---|---|
| Auth | Class-level admin-auth composite on every admin controller; the admin Basic Auth guard is never registered globally |
| One sub-module per resource | Each managed resource has its own module/controller/service/`dtos` |
| List response shape | `items` + pagination metadata, except the flat listings (categories, settings, and any `simple=true` variant); see the API contract reference |
| Status transitions | Order status changes go through the allowed-transition state machine, never an unchecked update |
| The admin surface returns rows whole | There is no response-DTO layer here, and reads are not narrowed to hide columns — a credential **hash** reaches admin responses (see `delivery-persons/AGENTS.md`). That is deliberate for an operator-only surface behind Basic Auth; it is *not* a licence to widen it to plaintext secrets or to carry the same openness into a client-facing module |
| Error handling | Translate Prisma errors to `AppException` via the `@shared/helpers/prisma-errors` predicates; register codes before throwing |
| Sort at the database first | Use `orderBy` (including `_count`) whenever Prisma can express it; the in-memory two-step fetch is the fallback, not the default, and exposing no sort key at all is a legitimate third answer |
| Every ordering ends on a unique column | Otherwise ties come back in whatever order Postgres happens to return, which shifts as rows are updated — under `skip`/`take` that duplicates and drops rows between pages, and on a flat listing it reshuffles the screen. Covers client-chosen sort keys, fixed orderings, `take`-capped windows, the ids query of an in-memory sort, and the nested reads that are ordered (a customer's order history, an order's items). One nested read is still outside it: a customer's address list has no `orderBy` at all, and needs an ordering chosen before it can have a tiebreaker. Exempt: an ordering already on a unique column, and single-row `findFirst` probes for a max, where any tied row gives the same answer |
