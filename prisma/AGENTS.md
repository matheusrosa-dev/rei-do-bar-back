# AGENTS.md — prisma/

## What belongs here

The database schema (the single source of truth for all models), migration history, and seed scripts. The Prisma client is generated from here into the shared database directory and is never edited by hand.

## What does NOT belong here

- Data-access logic → it lives in feature services, which inject `PrismaService`.
- Runtime config reading → the CLI reads the connection string via the root Prisma config file; application code reads config through `ConfigService`.

---

## Generator & Datasource

The client is generated in **CommonJS module format** to stay compatible with NestJS module resolution, and its output path points into the shared database directory (not `node_modules`). The datasource is PostgreSQL; the connection string is read from the environment by the root Prisma config file.

After any schema change, regenerate the client and update the Prisma mock used in tests if new model methods are now called.

---

## Schema Conventions

| Convention | Detail |
|---|---|
| Primary keys | String UUID, generated by default |
| Column naming | Database columns mapped to `snake_case` |
| Table naming | Tables mapped to `snake_case`, pluralized |
| Timestamps | `createdAt` / `updatedAt` on entities, mapped to snake_case columns |
| Monetary values | Stored as integer cents — never floats |
| Soft delete | Availability is an active flag; admin deletion of catalog entities is a nullable deletion timestamp, and all reads filter it out |
| Sequences | Human-friendly sequential numbers (where present) are backed by a Postgres sequence alongside the UUID id |

Planned-but-commented-out models must not be implemented until the feature is prioritized.

---

## Migrations

Use the project scripts (`migrate:dev` to create/apply in development, `migrate:deploy` for production, `generate` to refresh the client). Each migration is a timestamped folder containing its SQL.

**Destructive migration commands (reset/drop) require explicit user confirmation** — never run them autonomously.

---

## Seeds

The seed entrypoint bootstraps a Prisma client directly (outside NestJS DI) and runs domain seed functions in order. **Seed functions must be idempotent** — check for existing records and only insert what is missing.
