# AGENTS.md — prisma/

## What belongs here

The database schema (the single source of truth for all models), migration history, and seed scripts. The Prisma client is generated from here into the shared database directory and is never edited by hand.

## What does NOT belong here

- Data-access logic → it lives in feature services, which inject `PrismaService`.
- Runtime config reading → the CLI reads the connection string via the root Prisma config file; application code reads config through `ConfigService`.

---

## Generator & Datasource

The client is generated in **CommonJS module format** to stay compatible with NestJS module resolution, and its output path points into the shared database directory (not `node_modules`). The datasource is PostgreSQL; the connection string is read from the environment by the root Prisma config file.

After any schema change, regenerate the client and update the Prisma mock used in tests if new model methods are now called.

## Schema Conventions

| Convention | Detail |
|---|---|
| Primary keys | String UUID, generated by default — except join tables that carry no data of their own (e.g. `CouponCustomer`), which use a composite primary key on the FK pair |
| Column naming | Database columns mapped to `snake_case` |
| Table naming | Tables mapped to `snake_case`, pluralized |
| Timestamps | `createdAt` / `updatedAt` on entities, mapped to snake_case columns — join tables (e.g. `CouponUsage`, `CouponCustomer`) only carry `createdAt`, and so do append-only records of something that happened (movement ledgers, dispatch history), which are never updated after the insert |
| Event timestamps | The moment a domain event happened gets its **own nullable column**, written once at the transition — never inferred from `updatedAt`, which every later write to the row overwrites. Null means the event has not happened — or, on a column introduced without a backfill, that it happened before the column existed; a reader that windows or sorts on the column has to decide deliberately where those rows land |
| Enums | A closed set of domain values is a **schema enum** — the schema is its single source of truth. Application code re-exports the generated enum (from a module helper, or a shared types file when several modules need it) instead of redeclaring a parallel TypeScript enum, so adding a value means a schema change plus a migration, never an edit in two places |
| Monetary values | Stored as integer cents — never floats |
| Indexes | A FK gets an index when something queries **by** it, not because it is a FK; the unique constraints the model already declares are not repeated as indexes. A composite index is shaped by the `where` that needs it, never by the model: the equality column leads and the range-or-sort column follows, in that order, and a status paired with its **own** event timestamp is one index per pair rather than one over several timestamps. An index outlives the module that asked for it — several audiences usually filter on the same shape — so treat it as shared: adding one is local, dropping one is not. Document the reads it covers, and the ones it deliberately does not, in the `AGENTS.md` of the module that owns those reads |
| Soft delete | Availability is an `isActive` flag. Logical deletion uses a nullable deletion timestamp that all reads filter out — applied wherever a row must survive deletion (e.g. to preserve linked history); on records holding personal data, deletion also scrubs that data (anonymization) |
| Sequences | Human-friendly sequential numbers (where present) are backed by a Postgres sequence alongside the UUID id |
| Secrets | Only ever the **hash** of a credential, never the plaintext, in a column named for the hash it holds. A credential that an operator assigns after the fact is **nullable**, so the row can exist before it has one — and a null hash means "cannot authenticate", not "no password required" |
| Sessions | A revocable session is its own table holding the token hashes plus an explicit expiry column per token — expiry is data, not something inferred from `createdAt`. Limiting a principal to **one live session** is expressed as a `@unique` on the owner FK, so a new login is an `upsert` that replaces the old row rather than application code deleting the previous one; the FK cascades on delete so removing the owner cannot strand a usable token |
| Snapshots | Order rows denormalize purchase-time data (item details, delivery address, applied coupon code and discount) into their own columns so later changes never rewrite history; a snapshot may coexist with a nullable live reference to the source row (nulled on deletion) when the reference is needed operationally |

## Migrations

Use the project scripts (`migrate:dev` to create/apply in development, `migrate:deploy` for production, `prisma:generate` to refresh the client). Each migration is a timestamped folder containing its SQL.

**Destructive migration commands (reset/drop) require explicit user confirmation** — never run them autonomously.

A migration may carry a **data backfill** alongside its DDL when a new column has to mean something for rows that already exist. Backfilling from an approximate source is only acceptable where the approximation cannot be mistaken for the real thing.

When no existing column even approximates the event, the honest backfill is **none at all**: the whole history stays null and only new transitions stamp. That is the right call whenever the candidate source is overwritten by a later transition or by an unrelated write — such a value does not approximate the moment the event happened, it merely looks like it does. A non-terminal transition rarely has an acceptable source for this reason.

If any query reads the new column through a time window, the backfill must **stop at that window's boundary**, leaving the rows inside it null. A null says "unknown", which every reader already handles; a plausible-looking wrong value silently becomes a wrong answer.

If instead a query **orders** on the new column, the rows left null need a declared position: the default placement follows the sort direction and is an accident, not a decision. Choose the end that preserves the order those rows already had under the column being replaced, and state it in the query rather than relying on the database default.

A column no query reads yet may be backfilled in full — the values are historical record, not an answer to anything. Note that a window over the same rows often already exists on `updatedAt`; the comment must name it and say what happens the day that filter moves onto the new column, so whoever makes that move knows to null the rows inside the window first.

Either way, the comment says which source was used and why it stops where it does — or why it does not stop, or why no source was acceptable at all — and what the readers of the column do with the rows left null.

## Seeds

The seed entrypoint bootstraps a Prisma client directly (outside NestJS DI) and runs domain seed functions in order. It has to build the driver adapter itself, reading the connection string from the environment: the datasource carries no `url`, so a client constructed without an adapter has nowhere to connect. **Seed functions must be idempotent** — check for existing records and only insert what is missing. When the check compares seed data against rows already in the database, match on the **business key** (a `Set` of names/keys), never on array position: an index-based comparison against a `findMany` result is only correct when the table is empty or fully seeded, and silently duplicates or collides on any partial state. Where the name alone is not unique in the seed data, the key composes the fields that tell the rows apart — and editing one of those fields in the database makes the row miss the `Set` and be inserted again, so compose the key from the fields an operator is least likely to change.

Seeding is **gated by `NODE_ENV`**: the runtime settings seed always runs, while everything else — the demo catalog and the whole demo dataset — runs only in development. Three scripts expose this:

| Script | Behavior |
|---|---|
| `seed` | Forces `NODE_ENV=development` — seeds settings, the catalog **and** the demo dataset |
| `seed:reset` | Same, plus `SEED_RESET=true` — **wipes the demo data first**, then seeds it again |
| `seed:production` | Runs without the override — seeds settings only |

A new seed that inserts demo/fixture data belongs behind the development gate; one that bootstraps data the app requires to boot belongs outside it.

### Execution order

Order matters, because each seed re-queries what the previous ones wrote (no seed returns data to the next):

1. `seedSettings` — always.
2. `resetDemoData` — only with `SEED_RESET=true`, which is what `seed:reset` sets (development only, aborts otherwise). Deletes the demo tables in reverse-FK order, catalog included so stock returns to its catalog value; settings survive.
3. `seedCategories` → `seedProducts` — the catalog.
4. Everything below runs only when there is **no customer in the database**. That single guard covers the whole demo block: it is what makes a rerun a no-op instead of a second copy of the dataset — and, if a run fails halfway, what makes `seed:reset` the way back to a clean dataset.
5. `seedDemoSettings` → `seedCustomers` → `seedDeliveryPersons` → `seedCoupons` → `seedOrders` → `seedInventory` → `seedNotifications`.

`seedDemoSettings` activates the settings the demo store should exercise — the three monetary ones (delivery fee, minimum order value, welcome coupon), whose values it also overwrites, plus the alert and the WhatsApp contact, which it activates while leaving the value `seedSettings` wrote (the entry omits `value`, and Prisma reads `undefined` as "do not touch"). The two "store closed" messages stay inactive — active, either of them blocks order creation.

### Demo data conventions

- **The barrel is the entrypoint's only door.** `seed.ts` imports every seed from `seeds/index.ts`, so a new seed file that is not re-exported there simply never runs.
- **Shared demo vocabulary lives in one helpers module**, next to the `chance` instance: the pt-BR name/street/neighborhood pools, collision-free digit generation for phones and documents, the clock utilities every date is built from, the order-address snapshot format, and the pick/chunk helpers. Reach for those instead of reinventing them in a new seed.
- **Randomness is seeded.** `helpers.ts` exports a single `chance` instance built with a fixed seed, so the generated field values repeat run after run and a bug found in seeded data is reproducible — ids come from `randomUUID` and every date is measured from the current clock, so those two do move. Import that instance; never construct another `Chance`. For the same reason every `findMany` whose result feeds the generator carries an explicit `orderBy` — without it the database's row order silently decides the draw.
- **Domain invariants are the seed's responsibility.** Nothing goes through the services, so no event fires and no guard runs. The seed writes the event timestamps the transitions would have written (`shippedAt`/`deliveredAt`/`cancelledAt`, delivery person only from `SHIPPED` on) and keeps every derived timestamp in the past; it keeps at most one open order per customer **and places it after the last closed one**, since the app refuses a new order while another is in progress; it derives coupon discounts with the same formula the service uses, respects `usageLimit` and one use per customer, and derives both the coupon-usage row and the cancellation movement's origin from the same invariant — only the admin cancels after shipping, and only the customer's cancellation deletes the usage; it pads the items until the order total clears the active `MIN_ORDER_VALUE`; and it hands every non-deleted customer a cart, while addresses (one to three, exactly one flagged as main) go only to the customers that are complete enough to order — which is why the order seed filters on having a main address.
- **Ledgers are written by hand.** `seedInventory` derives one movement per order event, adds admin restocks/removals, and then reconciles `stockQuantity` from the resulting ledger — it is the only writer of stock after the catalog seed.
- **Bulk inserts.** Ids are generated with `randomUUID()` up front so parents and children can go in with `createMany` in chunks, instead of one nested `create` per row.
- **Import the rule when it is a pure shared helper; mirror it when it is not.** Totals, hashing and cutoff helpers are imported from the application code directly. A rule that only exists behind a Nest provider — a private method, or a constant whose module drags the DI graph into the seed — is copied instead, and the copy names its source in a comment so the two can be found together when one changes.
- **Credentials.** Only the delivery-person password is seeded (bcrypt hash of a demo password printed by the seed), because the admin picker only offers delivery persons that have one. OTP codes are seeded too, live and expired, because their hash is a plain digest of a generated code. Sessions and refresh tokens are not: their hashes are tied to a runtime secret or to a token nobody holds, so a seeded value there could never authenticate anyone.
